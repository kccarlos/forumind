# Development

How to build, run, and test Forumind from source. For how the code is
organized, see [ARCHITECTURE.md](ARCHITECTURE.md).

## Requirements

| Tool | Why |
| --- | --- |
| **Xcode 27** (macOS 27 or later) | Builds the app. The deployment target is iOS 17; Apple Intelligence features need a newer iOS (see [APPLE_INTELLIGENCE.md](APPLE_INTELLIGENCE.md)). |
| **Ruby** with the **`xcodeproj`** gem | Generates `Forumind.xcodeproj`. The system Ruby works: `gem install --user-install xcodeproj` (or use Homebrew/rbenv Ruby). |
| Rust (optional) | Only to refresh the ad-blocking filter lists (`brew install rust` or rustup). See [AD_BLOCKING.md](AD_BLOCKING.md). |
| Bundler + fastlane (optional) | Only for App Store uploads from your Mac (`bundle install`). CI does this for you. |

There are no Swift packages or other dependencies to fetch.

## Generate and open the project

The Xcode project is generated by `scripts/generate_project.rb` and committed.
Regenerate it after adding, removing, or renaming files or targets, or after
changing build settings in the script, and commit the result; CI fails if the
committed project doesn't match the generator.

```sh
gem install xcodeproj
ruby scripts/generate_project.rb
open Forumind.xcodeproj
```

Don't edit build settings in Xcode's UI: the next generator run overwrites
them. Change the script instead.

## Signing

The project is generated **without a signing team**, so it builds for the
simulator (and unsigned, with `CODE_SIGNING_ALLOWED=NO`) out of the box. To run
on a device, give the generator your Team ID in one of two ways:

```sh
# 1. A git-ignored file (remembered between runs)
cp Config/DevelopmentTeam.example.txt Config/DevelopmentTeam.txt
#    then replace ABCDE12345 in it with your Team ID

# 2. Or an environment variable (wins over the file)
DEVELOPMENT_TEAM=ABCDE12345 ruby scripts/generate_project.rb
```

Find your Team ID in Xcode › Settings › Accounts, or at
<https://developer.apple.com/account> under Membership details.

Don't commit a project generated with your team: run
`ruby scripts/generate_project.rb` without a team (move
`Config/DevelopmentTeam.txt` aside, or unset `DEVELOPMENT_TEAM`) before
committing project changes.

### iCloud sync (CloudKit) and signing

iCloud sync uses CloudKit, which only works in a build signed with the
iCloud entitlement; an app that calls CloudKit without it crashes. So the
generator turns CloudKit on **only when it finds a team**:

| Generated with | CloudKit | Entitlements the app is signed with |
| --- | --- | --- |
| No team (the committed project, CI, forks without a team) | off: no `CLOUDKIT_ENABLED`; Settings shows "Sync needs a signed build" | `Forumind/Forumind.entitlements` (App Group only) |
| A team | on: `-D CLOUDKIT_ENABLED` | `Forumind/Generated/Forumind.entitlements` (git-ignored) |

With CloudKit on, the generator writes
`Forumind/Generated/Forumind.entitlements` from the base file plus:

- `com.apple.developer.icloud-services` = `CloudKit`,
- `com.apple.developer.icloud-container-identifiers` =
  `iCloud.<BUNDLE_ID_PREFIX>` (the app reads it from `DCCloudKitContainer`
  in `Info.plist`),
- `aps-environment` = `development`, for the silent pushes that announce
  changes (exporting for TestFlight or the App Store switches it to
  `production`),
- and `com.apple.developer.private-cloud-compute` with `DC_ENABLE_PCC=YES`.

`DC_ENABLE_CLOUDKIT=YES|NO` overrides the default, for example
`DC_ENABLE_CLOUDKIT=NO` with a **free personal team** (free teams can't use
CloudKit). With a paid team, the first signed build with
`-allowProvisioningUpdates` (or Xcode's automatic signing) registers the
container and the iCloud and Push Notifications capabilities on the App ID.

**Don't strip signing from a CloudKit build.** A project generated with a
team compiles `CLOUDKIT_ENABLED` in; building it with `CODE_SIGNING_ALLOWED=NO`
removes the entitlement, and the app crashes when sync starts. For unsigned
simulator runs and tests, regenerate without a team (or with
`DC_ENABLE_CLOUDKIT=NO`), or build signed.

**Forks** must use their own container: `BUNDLE_ID_PREFIX` also sets the
container (`iCloud.<prefix>`), and containers can't be shared across teams.
Deploy the fork's CloudKit schema as described in
[SYNC.md](SYNC.md#cloudkit-schema).

**Testing sync** needs two devices (or a device and a simulator signed in to
iCloud) on the same Apple Account, both running a signed build. See
[SYNC.md](SYNC.md#testing).

### Forks and your own bundle ID

Every identifier comes from one prefix, `io.github.kccarlos.forumind`
by default. Bundle IDs are unique across Apple's whole system, so a fork that
signs for a device needs its own:

```sh
BUNDLE_ID_PREFIX=com.example.forumind DEVELOPMENT_TEAM=ABCDE12345 \
  ruby scripts/generate_project.rb
```

| Identifier | Value |
| --- | --- |
| App | `<prefix>` |
| Share extension | `<prefix>.share` |
| App Group | `group.<prefix>` |
| Keychain services, background task | `<prefix>.<name>` |
| iCloud (CloudKit) container | `iCloud.<prefix>` |
| Unit / UI tests | `<prefix>.tests`, `<prefix>.uitests` |

### Free (personal) team limits

A free Apple ID team can run the app on your own devices, with limits:

- Builds expire after 7 days; reinstall from Xcode.
- Free teams have a limited set of capabilities and a small number of App IDs.
  If Xcode can't register the App Group for your team, sharing from Safari
  still opens the app through the `forumind://` link; only the App
  Group inbox is unavailable.
- Apple Intelligence through Private Cloud Compute needs an entitlement Apple
  grants to a paid team.
- iCloud sync (CloudKit) needs a paid team: generate with
  `DC_ENABLE_CLOUDKIT=NO`. API keys still sync through iCloud Keychain, which
  needs no iCloud entitlement.

## Build and run

In Xcode, pick the **Forumind** scheme and a simulator or device.
From the command line:

```sh
xcodebuild build -project Forumind.xcodeproj -scheme Forumind \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  CODE_SIGNING_ALLOWED=NO -derivedDataPath /tmp/dc-dd
```

To run on a device, generate with your team (above), connect the device, pick
it in Xcode, and press Run. On first launch, trust the developer under
Settings › General › VPN & Device Management, and turn on Developer Mode if
iOS asks.

## Tests

### Unit tests

```sh
xcodebuild test -project Forumind.xcodeproj -scheme Forumind \
  -destination 'platform=iOS Simulator,name=iPhone 17' \
  -only-testing:ForumindTests CODE_SIGNING_ALLOWED=NO
```

- `ContentBlockingRulesTests` compiles every bundled filter-list chunk in the
  simulator's WebKit, so it takes a few seconds.
- The live NVIDIA NIM test runs only when `TEST_RUNNER_NVIDIA_API_KEY` is set
  in `xcodebuild`'s environment; otherwise it is skipped.
- `KeychainSyncTests` needs a signed build for real synchronizable Keychain
  items (unsigned builds get `errSecMissingEntitlement`, and those tests
  skip). Run them ad-hoc signed:

  ```sh
  xcodebuild test -project Forumind.xcodeproj -scheme Forumind \
    -destination 'platform=iOS Simulator,name=iPhone 17' \
    -only-testing:ForumindTests/KeychainSyncTests \
    CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM=
  ```

### UI tests

UI tests relaunch the app many times and keep its saved state between tests,
so use a simulator you aren't using for anything else. Build once, then run:

```sh
DEST='platform=iOS Simulator,name=iPhone 17'
xcodebuild build-for-testing -project Forumind.xcodeproj -scheme Forumind \
  -destination "$DEST" CODE_SIGNING_ALLOWED=NO -derivedDataPath /tmp/dc-dd-uitest
xcodebuild test-without-building -project Forumind.xcodeproj -scheme Forumind \
  -destination "$DEST" -only-testing:ForumindUITests \
  CODE_SIGNING_ALLOWED=NO -derivedDataPath /tmp/dc-dd-uitest
```

Use an iPad destination (for example `name=iPad Air 11-inch (M4)`) for the
side-by-side layout tests; iPhone-only and iPad-only tests skip themselves.

**Offline subset** (no network and no AI; uses the DEBUG sample data):

```sh
xcodebuild test-without-building -project Forumind.xcodeproj -scheme Forumind \
  -destination "$DEST" CODE_SIGNING_ALLOWED=NO -derivedDataPath /tmp/dc-dd-uitest \
  -only-testing:ForumindUITests/OnboardingUITests \
  -only-testing:ForumindUITests/SettingsNavigationUITests \
  -only-testing:ForumindUITests/ForumsHomeUITests/testAddForumSheetOpensFromTheForumsHome \
  -only-testing:ForumindUITests/PhysicalDeviceSmokeTests/testExpandedWorkspacesRenderMarkdownAndKeepChatComposerVisible \
  -only-testing:ForumindUITests/PhysicalDeviceSmokeTests/testManageRowsUseMailStyleSwipeActions \
  -only-testing:ForumindUITests/PhysicalDeviceSmokeTests/testAssistantPageStatesOffline \
  -only-testing:ForumindUITests/PhysicalDeviceSmokeTests/testAgentModeAndWatchedTopics
```

Notes:

- No test enters or saves an API key. `ShareHandoffUITests` skips if a
  provider is already configured on the simulator, so it never starts real AI
  work. `testAgentModeAndWatchedTopics` runs an agent with no key, so it fails
  at once without contacting any provider.
- Tests that load `meta.discourse.org` (the share hand-off and browser smoke
  tests) check that it's reachable and skip when offline.
- `testLiveSummaryAndChat` and `testLivePullPostResponsesSupportsExportAndChat`
  run only on a physical device with a configured provider, and make real AI
  calls: `-destination 'id=<device id>' -allowProvisioningUpdates`.
- To start from a clean slate, uninstall the app:
  `xcrun simctl uninstall <udid> io.github.kccarlos.forumind`.

## DEBUG launch arguments

DEBUG builds read these arguments for QA and screenshots. Set them in Xcode
(Product › Scheme › Edit Scheme › Run › Arguments) or pass them to
`xcrun simctl launch <device> io.github.kccarlos.forumind <args>`.
They never overwrite real saved data, and Release builds ignore them.

### Sample data (no key or network needed)

| Argument | Effect |
| --- | --- |
| `-dc-sample` | Loads offline sample data from three forums: Discourse Meta and two fictional ones on reserved example domains (required by the rest of this table). The Assistant opens by itself on iPhone. |
| `-dc-page-state <state>` | `loading`, `notForum`, `maybe`, `forumHome`, or `topic` (default). |
| `-dc-topic meta\|makers` | Which sample topic is open: Discourse Meta, or the fictional Maker Space Community. |
| `-dc-assistant-mode <mode>` | `summary`, `chat`, or `agent`. |
| `-dc-open-manage` | Opens Manage. |
| `-dc-manage-kind <kind>` | Manage filter: `all`, `summaries`, `agent`, `watched`, `activity`. |
| `-dc-no-provider` | Leaves the AI provider unconfigured. |
| `-dc-no-summary` | The open topic has no summary yet. |
| `-dc-summary-running`, `-dc-chat-streaming`, `-dc-agent-running` | Work in progress. |
| `-dc-chat-typing` | With `-dc-chat-streaming`: typing dots, no text yet. |
| `-dc-stale-summary` | The `makers` sample topic's summary is behind the topic (stale notice). |
| `-dc-scroll-sources` | Ask the forum: scrolls to the answer's sources. |
| `-dc-focus-chat` | Raises the keyboard in the chat composer. |
| `-dc-script <action>-after:<seconds>` | Changes state mid-use: `switch-provider`, `delete-key`, `remove-forum`, `unpin-forum`, `clear-all`, `reset-settings`. |

With `-dc-page-state topic` or `forumHome`, the browser also loads the real
forum page behind the Assistant, unless `-dc-forums-home` is also passed: then
nothing is loaded and the Forums home stays up (fully offline). The fictional
forums (`-dc-topic makers`) live on reserved example domains that don't
resolve, so use them with `-dc-forums-home`. Sample forums always show letter
monograms, never the forums' own icons. With
`-dc-apple-intelligence on-device` or `pcc`, the sample summaries, chats, and
runs are labeled as Apple Intelligence runs and it is the selected provider.

### Apple Intelligence

| Argument | Effect |
| --- | --- |
| `-dc-apple-intelligence <status>` | Forces the Apple Intelligence status shown in the app: `pcc`, `on-device`, `off`, `unsupported`, `downloading`, `language`, or `old`. A forced `pcc` only changes the label; requests still need the real model. |

### Forums and browser

| Argument | Effect |
| --- | --- |
| `-dc-seed-forums` | Pins three forums (Discourse Meta and two fictional ones) and adds two fictional recent ones (icons are fetched live unless `-dc-no-forum-icons`). With it or `-dc-sample`, the suggested forums are fictional too, so screenshots show no real companies. |
| `-dc-no-forum-icons` | Shows letter monograms instead of the forums' own icons (implied by `-dc-sample`). |
| `-dc-forums-home` | Starts on the Forums home. |
| `-dc-open <url>` | Opens a page on launch. |
| `-dc-show-switcher` | Opens the forum switcher. |
| `-dc-add-forum` | Opens the Add forum sheet. |
| `-dc-bar top\|bottom` | Browser bar position for this launch. |
| `-dc-content-blocking off` | Turns ad and tracker blocking off for this launch (settings unchanged). |
| `-dc-scroll-page <points>` | Scrolls each loaded page down. |
| `-dc-force-width <points>` | iPad: letterboxes the app to that width, with the size class a Split View window of that width gets. |
| `-dc-resize-demo [w1,w2,…]` | iPad: animates the window width through the list (default 1032, 800, 1032, 700, full), 6 s per step. |

### Onboarding and Settings

| Argument | Effect |
| --- | --- |
| `-dc-reset` | Shows the walkthrough again (no data deleted). |
| `-dc-onboarding-step <n\|name>` | Opens the walkthrough on a step: 1-based number, or `welcome`, `features`, `provider`, `forums`, `sync`, `share`, `privacy`, `done`. |
| `-dc-scroll-bottom`, `-dc-focus` | Walkthrough: scroll to the bottom / focus the key field. |
| `-dc-skip-onboarding` | Marks the walkthrough done. |
| `-dc-show-settings <page>` | Presents Settings: `root`, or a page: `provider`, `sync`, `forums`, `summaries`, `agent`, `watched`, `browser`, `data`, `help`, `sharing`, `about`, `acknowledgements`. |
| `-dc-panel-settings [page]` | Opens Settings inside the Assistant panel. |

### Sync

| Argument | Effect |
| --- | --- |
| `-dc-keychain-sync-probe` | Checks that synchronizable Keychain items work with this build's signing: adds, reads back, and deletes a test item, then shows the result in an alert and prints `DCPROBE` log lines. Skips the walkthrough so the alert can show. |
| `-dc-sync-status <status>` | Shows a fake sync status in Settings › iCloud Sync and the walkthrough (the toggle follows it): `off`, `noAccount`, `restricted`, `unavailable`, `syncing`, `upToDate` (or `on`), `error`. The engine is untouched. |
| `-dc-sync-explain` | Settings › iCloud Sync: expands "What syncs". |
| `-dc-cloudkit-probe` | CloudKit builds: logs the iCloud account status and a save/fetch/delete round trip through a test record. |

Sync stays off under `-dc-sample` and the UI tests' `-ui-test-*` arguments,
so sample data never reaches iCloud.

UI tests also use `-ui-test-sample-session`, `-ui-test-manage-swipe`, and
`-ui-test-pull-mode`.

To run the Keychain probe on a device:

```sh
xcrun devicectl device process launch --console --device <device id> \
  io.github.kccarlos.forumind -dc-keychain-sync-probe
```

## Updating the ad-blocking lists

A weekly workflow opens a pull request with fresh EasyList/EasyPrivacy rules.
To do it by hand (needs Rust and Python 3):

```sh
scripts/adblock/update_rules.sh     # download, convert, validate, write
scripts/adblock/run_tests.sh        # converter tests
```

Then run the unit tests and commit `Forumind/ContentBlocking/`. See
[AD_BLOCKING.md](AD_BLOCKING.md).

## Platform notes

- iOS can suspend the app in the background. Queued work is saved and resumes
  on the next launch, but a network stream can't be guaranteed to keep running
  while another app is in front. Browsing inside the app never interrupts a
  running summary or chat.
- Local models: Ollama and LM Studio are reached over the local network
  (`NSAllowsLocalNetworking`); iOS asks for local-network access the first
  time.
